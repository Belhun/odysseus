## Title/topic

What UI framework SysForge uses (Avalonia + MVVM), and why the app still “goes outside” Avalonia for navigation, DI, cross-screen events, and code-behind keyboard/focus.

## Features

No new product feature. Chat documents the **existing stack and shell architecture**:

| Layer | Concrete names |
|--------|----------------|
| UI | Avalonia 11.3 (Fluent theme), `.axaml`, classic desktop lifetime (`Program.cs` → `BuildAvaloniaApp().UseReactiveUI().StartWithClassicDesktopLifetime`) |

## Issues/bugs

No new bug filed or fixed. Chat **re-states a known lifecycle hazard**:

- **Duplicate `CurrentView` assign:** navigation can set `CurrentView` twice with the **same** control instance (`ViewChanged` + direct assign). Unsubscribing before `SetProperty` on a no-op assign can drop handlers (e.g. dashboard `CardClicked`) without re-attaching. Workspace rule / `MainWindowViewModel.CurrentView` uses `ReferenceEquals` before unsubscribe.

Other “outside framework” items are intentional design, not defects:

- Avalonia has no full product shell (no built-in nav stack / region manager / ASP.NET-style DI).
- Pure XAML/bindings are weak for nested keyboard, focus chains, save-on-blur-style desktop UX → code-behind.
- Mixing ReactiveUI app hook with CommunityToolkit VMs can confuse contributors (two MVVM styles).

## UX

Explains desktop UX that bindings alone do not cover well:

- **Drafts inline rename:** Enter commits (`SaveRenameCommand`), Escape cancels (`CancelRenameCommand`) in `DraftsView.axaml.cs`.
- **Invoice calculator:** large code-behind for focus restoration and walking the visual tree (`InvoiceCalculatorView.axaml.cs`).
- **Shell navigation:** content switch is `CurrentView` host, not Avalonia `Frame`/router; dashboard cards and calculator→drafts flows rely on manually wired events.
- Mental model offered: Avalonia = paint/input/bindings; services + VMs = product behavior; code-behind + custom nav = gaps Avalonia does not bless.
